## TL;DR

Retire the 15-minute stateless tick and replace it with a **resident driver**: one long-lived orchestrator session per active epic that holds the dependency graph and decision-register canon in context, dispatches lanes, and advances on **completion events** instead of clock ticks. Cron survives in exactly two demoted roles — a slow **liveness guard** that boots a fresh driver only when the epic has actionable work and no live driver, and the daily **reconcile janitor**. The 2026-07-04 trial showed the tick's structural defects (time-triggered runs overlap the work they trigger; full context reconstruction per action) and proved the chassis worth keeping (cold-boot from durable state, claims under live contention, unattended evidence discipline). Driver mutual exclusion is a **new fenced driver-claim mechanism** (own comment species, session-run identity, stale-claim-closing takeover, session-process-watching refresher, freshness-checking fence); per-ticket claims gain session identity with a driver-claim-topped **liveness hierarchy**. Worker completion is detected by the transcript's terminal record with empirically validated mechanics, lane awaits are dual-wake, the merge close-out is fail-closed on the coherence gate, and every unverifiable harness behavior sits in a seven-item **live-test gate**. `pickup-next` ships intact-but-fenced in 0.14.0 and is deleted in 0.14.1 after the gate passes. The state machine, evidence rules, coherence gate, register, and both human gates carry over; the drive mechanism changes, the chassis stays.

## Key Points

- **Time was the wrong trigger.** Lane completion, gate answers, and blocker clearances are events the driver observes directly; fixed-interval polling either overlaps the work or idles. Same disease as mtime-polling in `await-worker.sh`, one level up; both fixed by one principle: **detect by content and event, never by clock or silence.**
- **One resident driver per active epic** (`drive-epic`, new skill, `model: sonnet`), running lanes **serially — one lane in flight at a time** (`maxParallelLanes` = 1 in 0.14, matching the 0.12 serial default; parallel lanes are a future release): boots from durable state once per session, selects actions by the tick's priority table, dispatches a lane, awaits it to close-out, then re-selects — so at any park evaluation no lane is in flight *by construction* (awaiting an in-flight lane is itself an available action, reached before park). Advances on completion — until **park** (no automated action possible: human-parked, blocked, or empty queue → brief, release, exit) or **bloat** (context degraded: await the in-flight lane's own exit — the driver cannot command a mid-flight checkpoint — then brief, release, exit; crash recovery is the floor if the exit protocol degrades). **No third exit trigger** — a time-based succession rule would recreate the conflicting-rule-set problem.
- **The supervisor is cron + a guard, not a new judge.** The hourly task invokes `drive-epic`; step 0: heartbeat, driver-claim liveness check; live driver → no-op exit; stale/absent claim + actionable work → fenced acquire and **become** the driver. (The wedged-driver probe lives in the daily janitor, not this guard — under same-task no-overlap the hourly guard cannot fire against the live driver it would probe.) Restart latency worst case ≈ staleness threshold + cron interval (~45 + 60 min); manual invocation is the identical code path, immediate.
- **Driver claims are their own comment species** (`# Driver Claim`), structurally invisible to `claim.sh`/`release-claim.sh` (both filter on the `# Ticket Claim` prefix), with one script — **`driver-claim.sh`**, subcommands `acquire | refresh | verify | release | status` — and their own template, living on the **epic ticket**. `status` is the read-only "does a fresh open driver claim exist" probe the guard and the fenced tick need before any mutation: `verify` cannot serve them (it is the own-claim fence — for a session holding no claim it conflates "none exists" with "fresh foreign exists"), and `acquire` must never be used as a probe (a probe that wins becomes a zombie driver claim). Acquire: close stale open driver claims first (re-reading staleness immediately before the close mutation), post, settle, read back; **oldest *fresh* open wins** by client-side `createdAt`, comment-id tie-break; lose → self-close and exit no-op. The **fence** (before every durable-write close-out, on every wake, and **immediately before the merge command** — the driver's one irreversible shared-state write; it is `gh pr merge`, not a git push): own claim open ∧ own session id ∧ oldest-fresh ∧ refresher alive; ownership lost → abort durable writes and exit; read error → brief retry, then exit without durable writes. Close-outs are **prefix-resumable** by the successor. Release closes own claim by id, with exit state; no attempt counters — succession is normal operation.
- **The refresher watches the *session process*, not its own parent.** Empirical finding: a background shell's parent is a zsh wrapper that **survives session death** — polling it would keep a corpse's claim fresh forever. The refresher captures the session process (the wrapper's parent at launch) and self-exits on its disappearance, detected by reparenting/PPID-change rather than `kill -0` alone (which reports a freshly-dead process alive during the zombie window). It bumps the claim every ~15 min by mutating content (Linear's `updatedAt` bumps only on meaningful change); staleness > ~45 min ⇒ dead driver. Background-shell lifecycle and longevity are live-test gate items.
- **Per-ticket claims gain session identity, and the progress test becomes a liveness hierarchy — deliberately amended, not carried.** "Same host = same actor" died with the serialized tick. Every claiming session mints a run id (the driver at boot; any lane/manual/tick session at invocation); claims record it; foreignness is session-scoped. Legacy claims without a session id are judged by the lease test alone. And the 0.13 progress rule "fresh checkpoints since the claim's last update ⇒ alive, regardless of age" becomes a **liveness hierarchy**: (1) a claim whose session id matches a **fresh open driver claim** is alive, full stop — the refresher makes session liveness directly observable, protecting legitimately quiet long lanes (a 3-hour review loop posts no checkpoints) from being beheaded; (2) else, fresh checkpoints within one lease window of *now* ⇒ alive; (3) else the lease-age test. The old rule made a crashed session's checkpointed claim immortal; the time-bound alone would have traded that wedge for a daily live-steal — the hierarchy closes both. `release-claim.sh` releases own-session claims by default; releasing a *foreign* claim requires an explicit flag **and the target claim's id** — never most-recent-open selection, because post-crash tickets normally carry a dead claim *and* a live successor claim, and the janitor must not close the wrong one. The asymmetry (claim refuses foreign, release can act on foreign, explicitly targeted) is intentional and stated. Tier-1's epic-locating mechanism is pinned — `claim.sh`'s surface carries no epic id, so it resolves the epic by parent traversal **to the parentless root** (`issue.parent`, hopping until parentless — one hop today, future-proof against sub-epics; a parentless claimed ticket *is* the epic, and driver claims are then on the claimed ticket itself) — and tier-2 counts only checkpoints **attributable to the claim's session** (legacy id-less claims: lease test only). One residual is stated honestly rather than papered over: a *manual* session's legitimately quiet multi-hour lane has no refresher and no checkpoints, so it is still beheadable at tier-3 — identical exposure to the 0.13 rule, no regression, and mitigated by discipline the surface already supports (manual long lanes checkpoint once per lease window, or pass a longer `lease_hours`).
- **Driver lane awaits are dual-wake with dedup.** Native completion notification primary; background v2 await backstop; both channels are live-test items; pinned fallback is foreground chunked awaits. Manifest reap-records dedup double-fires — wakes for already-reaped entries are ignored.
- **Await v2 is empirically validated, failure modes included.** Content-check loop on the transcript's **final lines** (never whole-file grep) every few seconds, mtime stall alarm in the same loop, `STALLED` a distinct exit, chunked ≤9-min Bash calls (harness caps verified: 600s max, 120s foreground default). Measured ~1s match latency; works when the file doesn't exist yet. **Truncation guard**: after match, confirm record completeness (trailing newline or one stable re-poll) before extracting.
- **STALLED never re-dispatches beside a live worker — and its confirmation can't deadlock.** RESUMABLE re-dispatch requires stopping the predecessor via the agent-layer primitive and confirming it is finished. Whether a force-stopped worker's transcript receives an `end_turn` record is uncharacterized, so confirmation semantics are: terminal record, **or** stop-success + transcript quiescence (mtime stable, no new writes) — and gate item 4 now characterizes the post-stop transcript shape. "Durable checkpoints" means checkpoints **new since this dispatch**.
- **The merge close-out is fail-closed on the coherence gate.** Ordering: apply `coherence-pending` **before** the merge command — a crash between merge and label under the old order left a merged child with no coherence review and no detector (the driver's idempotence check is label-gated; the PM's GitHub integration advances the child event-side, erasing the janitor's trigger). Belt: a **set-difference driver boot audit** — fetch all merged child PRs targeting the epic branch (`mergeCommit` oids, the same surface `verify-merge.sh` reads; `--limit` above any plausible child count) and all register-entry `Merge SHA:` keys from the epic (a paged read — it joins the comment-window-honesty rule): **every merged SHA must hold a register entry**, full stop. Any merged-but-unregistered SHA ⇒ `coherence-pending`, and **remediation is re-coupled to detection**: the review action targets exactly the unregistered set, oldest `mergedAt` first, serially, each dispatch noting that register entries newer than the SHA under review are not precedent. **Definitions, stated once and referenced everywhere**: *pending-human* ≡ a GATE1_AMENDMENT/GATE1_REFRESH verdict awaiting its ruling — the only verdicts whose routing cannot complete without a human; a fully-routed ALIGNED, MINOR_DRIFT, MATERIAL_DRIFT, or LEGITIMATE_DIVERGENCE is **clean** in this sense (its register writes, corrective ticket, and realignment complete in-route per the 0.13 verdict table) and neither halts remediation nor holds the label. (ALREADY_REVIEWED — the reviewer's no-op verdict when its SHA already carries an entry, reachable on a settle-lag race despite the loop-side idempotence check — is a clean no-op that writes no register entry, so the register-entry-based predicate never sees it.) **Halt** = complete the current SHA's own routing writes, then review no further SHAs while a pending-human verdict stands (reviewing against a register awaiting amendment is the waste the 0.13.4 blocking scope names). *unresolved* ≡ a pending-human entry with no later `RULING` register entry for its SHA — client-side `createdAt` with comment-id tie-break, fully successor-evaluable. (GATE1_AMENDMENT/REFRESH are *flags* on a verdict per the 0.13 output contract; "pending-human verdict" names a verdict carrying either flag.) **How a pending-human entry is resolved — the escalation contract and the per-flag routing — is defined once in the *Human-Ruling Resolution Route* section and referenced, never restated, everywhere else** (the human resolves it out-of-band by running `rule-coherence`; the guard, boot queue, and tick simply no-op on it). **The label clears iff the set-difference is empty ∧ no register entry over the epic's merged SHAs is unresolved** — **register-wide, never batch-scoped** (a batch-scoped conjunct clears over a predecessor's pending amendment one succession hop later), and an unresolved entry gates further remediation reviews, the boot queue, and the guard's actionable-work test: halted-pending-human is a durable park-shaped no-op until the human runs `rule-coherence`. No merged child PRs ⇒ vacuous pass, and a `coherence-pending` label with zero merged child PRs clears vacuously (the first-ever-merge crash prefix, whose "this merge SHA" query is otherwise ill-formed). No watermark, no bound: an earlier draft's "newer than the newest register entry" silently assumed register append-order — the very invariant the audit exists to backstop — and let a slipped merge hide behind a later reviewed one; the set difference needs the same two reads and makes the belt genuinely **independent of every producer honoring the merge discipline**. Git topology cannot carry this key: children are squash-merged (plain commits, indistinguishable from maturity push-backs), so `git log --merges` finds nothing and "newest commit" false-positives — both natural git-side readings are defect generators. Two crash prefixes, distinguished: **pre-merge** (label applied, merge never ran — no routing writes exist; resolve via the clear predicate, whose set-difference is unchanged, then reselect the merge) and **post-verdict partial routing** (resume the missing SHA-keyed writes). PR-list reads are assumed read-consistent (one sentence of settle discipline if field behavior says otherwise), and the `--limit` gets the same honesty treatment as comment windows: page, or assert merged-PR count < limit. **The merge action is ineligible while `coherence-pending` is set** — the 0.13.4 blocking scope listed only canon-consuming dispatches, and with two ready children a literal reading merges B before A's review; the invariant keeps reviews serial and the register append-ordered, and the set-difference audit backstops any producer that breaks it.
- **The wedged-driver probe counts only real progress.** Signal: lane checkpoints, state/label changes (derived from issue *history* — labels carry no attach-timestamp), register entries — **excluding bookkeeping species** (heartbeats, janitor notes, takeover notes, briefs), which otherwise reset the clock every time the monitor itself writes. Species discrimination is header-based, and the canonical mapping is a **tagged partition, not the raw template directory** (the template set is an identification surface, not a classification — it contains bookkeeping headers like Ticket Claim and Continuation Brief, while the highest-volume progress species has no template at all): each ticket-comment header is tagged progress or bookkeeping in one pinned table; **lane checkpoints get a pinned header** (a new `lane-checkpoint.md` template replaces the undefined "standard PM comment"); the heartbeat line gets an explicit non-template carve-out (bookkeeping); **unknown headers default to bookkeeping** — never progress, so novel comment species can mask neither a wedge nor a theft. One partition, consumed identically by this probe, `claim.sh`'s liveness test, the janitor's expiry, and `watchdog-scan.sh` — and **canonical in one plugin-shipped data file** (`dodi-dev/scripts/comment-species.sh`, sourced by the scripts; the guard probe and the janitor consume it through the species-aware `watchdog-scan.sh` rather than re-classifying inline). Repo-root `templates/` is a validation mirror, not a runtime surface — plugin sessions run in target-repo worktrees where this repo's files don't exist, so a table "shipped with the templates" would have forced four inline copies with no sync check, the exact drift the partition exists to prevent. Fresh claim + no progress-species writes > 8h ⇒ escalate. Nested one-query shape per the `watchdog-scan.sh` precedent, with a paged/split fallback if query-complexity limits bite. It runs in the **daily janitor sweep** — the hourly guard cannot fire against the live driver it would probe under same-task no-overlap — so its honest detection latency is ~a day.
- **The daily heartbeat: one canonical location, real mechanics.** Posted/refreshed on every guard path to the **designated heartbeat location** (task input) — canonical for the dead-man check so the observer always knows where to look — with an optional mirror on the active epic. Per-day dedupe (update-in-place, not create-per-day) moves into `heartbeat.sh`; its default note string ("tick alive") and header are updated with it.
- **Manifests are anchored to absolute paths, never cwd.** Agent-thread cwd resets between Bash calls, so "the session's cwd" was fiction for lanes. The driver's manifest lives at the epic worktree's absolute path; a lane's at its ephemeral worktree's absolute path — recorded **as an absolute path** by `pickup-ticket` at creation (the property is load-bearing, so `pickup-ticket` joins the closure to enforce it). Per-session filenames (`.dodi/dispatch-manifest-<session-run-id>.jsonl`), `session_id` in the schema, reap records appended, self-ignoring `.dodi/.gitignore` (empirically verified).
- **The reaper classifies and reports; only the agent layer stops.** Nested stop-primitive availability is gated; where absent, orphaned grandchildren run to completion — note and escalate.
- **Maturity work: ephemeral worktrees with per-gate push-back** — push at each gate transition *before* that gate's comment/label (`dispatch-eligible.sh` checks labels, not artifact presence); SHAs cited only post-push (patch-id fallback). Layering rule: **claims serialize tickets; worktrees serialize files; nothing serializes runs.** The driver is the epic worktree's only writer.
- **The 0.14.0 coexistence window has an operator contract.** `pickup-next` ships intact as the gate-fail fallback but **fenced**: its claim step calls `driver-claim.sh status` — fresh open driver claim ⇒ exit no-op — **re-verified immediately before the merge command itself** — the sentence governs the inlined `submit-ticket-pr` Merge sequence, since pickup-next's own step list contains no push step (single-shot fencing is one-directional: a driver booting minutes after the tick's claim would otherwise merge concurrently with it — the re-verify closes the double-merge race and bounds unreviewed-merge latency; the set-difference audit catches any slipped merge at the next boot, so nothing is permanent, and the fence keeps it from happening at all). The merge-ineligible-while-`coherence-pending` invariant binds the fenced tick identically. The same edit updates the skill's stale progress-test sentence to the amended liveness hierarchy — live prose must not command the dead rule the script under it no longer implements — **inverts the tick's own close-out to label-before-merge** (the edit touches that step anyway; the old ordering left a crash window that gate-fail revert mode, where no driver ever boots to run the audit, could never repair), and adds the **merge-ineligible-while-`coherence-pending` guard to the tick's merge selection** (step 2.1) so the invariant that "binds the fenced tick identically" has an implementing edit rather than a declaration; the tick's coherence-review step (2.2) is rewritten from "this merge SHA" to the full set-difference protocol — target set oldest-first with the not-precedent note, halt-after-routing-the-first-pending-human-verdict, the register-wide set-empty ∧ no-unresolved clear predicate (a pending-human entry is a no-op park — the human resolves it via `rule-coherence`, so the tick needs no wake edge), and the vacuous zero-PR clear (the inversion without the 2.2 rewrite would manufacture the ill-formed-query wedge in exactly the revert mode where no driver boots). Independently, the set-difference boot audit surfaces any merged-but-unregistered SHA whenever a driver next boots — the belt no longer relies on any producer. "Paused" means: task disabled in the scheduler, manual invocation safe (the fence makes it a no-op against a live driver). The transient doctrine contradiction (intact `pickup-next` prose still says claims are "not locking" while the new AGENTS.md says "claims serialize tickets") is accepted for the window and dies with 0.14.1.

## Why the Tick Model Falls

The 0.13.x tick (`pickup-next`): fresh session, full reconstruction, one action, exit. The 2026-07-04 trial (two maturity lanes, DOD-727/728) surfaced: (1) **overlap by construction** — 60–90-min runs against a 15-min cadence; one manual run beside the cron put two ticks in one epic worktree; (2) **reconstruction tax per action**; (3) **the stall** — a plan-reviewer improvised sub-workers and yielded for a notification that never arrives for nested dispatches; recovered by a human nudge, disqualifying for lights-out. What the trial proved carries forward: cold-boot from durable state works end-to-end; per-ticket claims held under live contention; evidence discipline held unattended.

## Driver Mutual Exclusion (new machinery)

`claim.sh` cannot carry the driver claim (no read-back, release-by-most-recent, no refresh primitive, attempt counters — and, pre-0.14, host-only identity). Driver claims are a **distinct comment species** — `# Driver Claim`, never `# Ticket Claim` — living on the **epic ticket**, served by **`driver-claim.sh`** (subcommands `acquire | refresh | verify | release | status`; one script, so the validator array gains it, `reap-workers.sh`, and the `comment-species.sh` partition file), with template `templates/ticket-comments/driver-claim.md`.

- **Identity:** session run id, minted at boot, recorded in the claim.
- **`acquire`:** close any stale open driver claims first, with a takeover note, re-reading staleness immediately before the close mutation (a recovering refresher at the 45-min edge must not be beheaded on a stale read); post own claim; settle (read-replication lag); read back all open driver claims; win iff own is the oldest **fresh** open by `createdAt` (client-side — refresh bumps `updatedAt`; connection order lies), comment-id tie-break; lose → close own, exit no-op. Exact-`createdAt` both-yield self-heals next guard hour. Read-back failure → close own if possible, else exit and let it go stale.
- **`refresh`:** session-lifetime background shell; bumps the claim every ~15 min by mutating content (a refreshed-at line). **Watches the session process, not its own parent**: empirically (this harness), a background command's chain is command → zsh wrapper → session process, and the wrapper *survives session death* — so the script captures the session process at launch (the wrapper's parent) and self-exits when it disappears, detected by reparenting/PPID-change rather than `kill -0` alone (zombie-window false-alive). Staleness > ~45 min ⇒ dead driver.
- **`verify` (the fence)** — before every durable-write close-out, on every wake, and immediately before the merge command: own claim open ∧ own session id ∧ own is oldest-fresh-open ∧ refresher alive (dead → restart or exit gracefully). Ownership lost → abort all durable writes, exit. Read error → brief retry, then exit without durable writes.
- **Prefix-resumable close-outs.** Any close-out can be interrupted at any write; every close-out sequence must be resumable from any prefix by the successor — the SHA-keyed coherence-review idempotence (0.13.4), generalized. Manifest reap-records, claim ids, and SHA-keyed evidence are the resume keys.
- **`release`:** close own claim by id, with exit state (`parked | bloat-handoff | refresh-park | no-op | ruled | taken-over | error`; `ruled` is the ruling-mode exit, which routes a human ruling and exits without entering the drive loop; `refresh-park` is the planned count-based context-refresh exit; `taken-over` is a stale-close by a successor). No attempt counters.
- **`status`:** read-only — does a fresh open driver claim exist, and whose. Consumed by guard step 0 and `pickup-next`'s fence; neither `verify` (own-claim fence — conflates "none exists" with "fresh foreign exists" for a claimless session) nor `acquire` (a probe that wins is a zombie driver claim) can substitute.
- **Takeover reaps the predecessor's lanes, then adopts its ticket claims.** Having closed a stale driver claim, the successor holds proof of that session's death. **First it reads the predecessor's dispatch manifest (per-session filename at the epic worktree's absolute path) and reaps/stops/confirms any non-terminal lane workers** — because whether an in-flight Agent-tool lane survives its dispatching session's *death* is a live-test-gate item, and if it does, foreign-releasing the ticket and re-dispatching would land a second lane beside a still-writing orphan (the round-3 "never re-dispatch beside a live worker" hazard, reachable through the takeover door the STALLED fix does not guard). Only then does it **foreign-release (by id) the per-ticket claims bearing that session id** — a drive-epic boot step, right after acquire (the children-scan uses the same nested-query shape as the watchdog). Without the adoption a dead predecessor's ticket claims ride tier-2 on pre-crash checkpoints for up to a lease window, idling resumable work; without the reap-first ordering the adoption itself re-opens the concurrency hazard.
- **Comment-window honesty:** claim reads (both species), the heartbeat dedupe read, **the boot audit's register-entry read, the review idempotence check, and the guard's unresolved-entry / resolved-but-labeled backstop read** page beyond `comments(last: 50)` or filter server-side; an open claim pushed out of a fixed window reads as "none," and a register entry pushed out would false-flag a reviewed merge (the guard's newest-biased window failures self-heal — a spurious boot's paged read re-parks).

**Per-ticket claims change deliberately:**

1. **Session identity.** Every claiming session mints a run id at start (driver at boot; lanes, manual sessions, and the intact 0.14.0 tick at invocation); `claim.sh` records it; foreignness is session-scoped regardless of host. Claims lacking a session id (posted by a still-open 0.13.x session) are judged by the lease test alone.
2. **The progress test becomes a liveness hierarchy — an amendment, not a carry-over.** Old rule: fresh checkpoints since the claim's last update ⇒ alive regardless of age. Under session scoping that immortalizes a crashed session's claim; a bare time-bound instead lets the janitor behead a live lane in a long quiet stretch (a multi-hour review loop posts no checkpoints — normal, per the trial). New rule, in order: (1) claim's session id matches a **fresh open driver claim** ⇒ alive (the refresher makes session liveness directly observable — dead sessions decay in ≤45 min, live ones are protected indefinitely); (2) checkpoint progress within one lease window of **now** ⇒ alive (covers manual sessions holding no driver claim); (3) else the lease-age test. Same protective intent — never steal a live claim — without wedging crashed-session tickets until the 3-day watchdog.
3. **Release ownership and targeting.** `release-claim.sh` releases own-session claims by default; releasing a foreign claim requires an explicit flag **and the target claim's id** — never most-recent-open selection (post-crash tickets normally hold a dead claim *and* a live successor claim; the janitor must close the one it judged, not the newest). The janitor's expiry re-reads staleness immediately before the close mutation, mirroring acquire's takeover re-read. Claim-side refusal strict, release-side override explicit and targeted — the asymmetry is intentional.

## The Resident Driver: `drive-epic`

New skill (`model: sonnet`); absorbs `pickup-next`'s machinery and replaces its trigger model.

### Contract

| Trigger | Inputs | Outputs | Durable writes | Allowed delegation | Failure states |
| --- | --- | --- | --- | --- | --- |
| hourly liveness cron, or manual invocation | PM scope, repo path(s), heartbeat location, retry ceiling (default 3), optional humanContact | epic advanced through as many actions as fit before park/bloat, or a clean no-op | driver claim + refreshes, continuation brief, daily heartbeat, everything the lane skills write | same set as `pickup-next` + state-reader/evidence-checker workers | PM unreachable, claim yield, retry ceiling, fence trip, tool/auth failure |

### Step 0 — the guard

1. **Daily heartbeat** — post/refresh (dedupe and update-in-place inside `heartbeat.sh`) at the designated heartbeat location; optional mirror on the active epic. Posted on every guard path **and refreshed by the driver in its own drive loop** — because if the scheduler's same-task no-overlap guarantee holds (see the live-test gate), the hourly guard cannot fire while a driver run is live, so a driver run crossing ~24h would otherwise starve the dead-man switch and fire a false substrate-death alarm; the in-loop refresh closes that.
2. **Driver-claim check** (`driver-claim.sh status`). Fresh live claim → exit, one line logged. Stale/absent + actionable work → `driver-claim.sh acquire`; win → this session is the driver. No actionable work — including an epic parked on an unresolved pending-human entry — → exit; the janitor's digest owns the human reminder. The human resolves it out-of-band by running `rule-coherence` (per the *Human-Ruling Resolution Route* section — a session, not a comment the guard must detect), so there is no wake edge to evaluate here. **Backstop:** an epic that is `coherence-pending` with the set-difference empty **and** no unresolved entry (a ruling session crashed between its `RULING` write and its in-session clear) *is* actionable — boot to evaluate the clear predicate — so a resolved-but-still-labeled epic never strands.
3. **Second signed-off epic in scope → escalate**, never interleave.

(The wedged-driver probe is *not* a guard step — it re-homed to the daily janitor sweep, since under same-task no-overlap the hourly guard cannot fire against the live driver it would probe. See Janitor Changes.)

Manual sessions run the identical step 0; per-ticket session claims enforce the same discipline for manual *lane* work.

### Boot

Mint the run id; start the refresher; **coherence audit** (set-difference): every merged child PR targeting the epic branch (`mergeCommit` oids) must hold a register entry — paged register read; any unregistered SHA ⇒ treat the epic as `coherence-pending` and queue the review for the unregistered set, oldest `mergedAt` first (the fail-closed belt for interrupted merge close-outs — including manual-tick merges during the 0.14.0 window); an unresolved pending-human entry parks the queue instead — no further reviews until the human resolves it via `rule-coherence` (per the *Human-Ruling Resolution Route* section), which writes the `RULING` out-of-band; no merged child PRs ⇒ pass, and a stray `coherence-pending` with zero merged PRs clears vacuously. Dispatch the state-reader (Fast tier); read the register canon and latest continuation brief; load the state tables; initialize the manifest at the epic worktree's absolute path. The driver works against the epic worktree **by absolute path** (cwd is not load-bearing — it resets between Bash calls) and is that worktree's sole writer; all lane work happens in per-lane ephemeral worktrees.

### Drive loop

Repeat until park or bloat:

1. **Select** by the tick's priority table (merge → coherence review → epic PR → resume RESUMABLE → deliver-ticket → mature-ticket), same demotion rules and `coherence-pending` blocking scope — **which now explicitly includes the merge slot: no merge action is eligible while `coherence-pending` is set** (this extends the 0.13.4 dispatch-only scope; it keeps reviews serial and the register append-ordered, with the set-difference audit as the producer-independent backstop, and the epic-orchestrator's "only then take the next merge" becomes canon rather than one of two competing texts). **Merge-action ordering is fail-closed: apply `coherence-pending` before the merge command** (the irreversible write is the inlined `submit-ticket-pr` merge itself), with the fence verified immediately before it. The coherence-review action targets every merged-but-unregistered SHA, oldest `mergedAt` first, serially, halting after the first pending-human verdict completes its own routing (definitions in the merge-close-out Key Point); the label clears iff the set-difference is empty ∧ **no register entry over the epic's merged SHAs is unresolved** — register-wide, never batch-scoped; an unresolved pending-human entry gates further remediation, the boot queue, and the guard's actionable-work test until its `RULING` entry lands — written out-of-band by the human's `rule-coherence` session (per the *Human-Ruling Resolution Route* section); zero merged child PRs clears vacuously.
2. **Claim** the ticket (session-identified per-ticket claims).
3. **Act**: dispatch with tier pins; append to the manifest (absolute-path anchored). Await dual-wake; wakes for reaped entries ignored. On `STALLED`: stop the worker (agent-layer primitive) and confirm it finished — terminal record, or stop-success + transcript quiescence; then RESUMABLE iff durable checkpoints *new since this dispatch*, else one no-progress attempt toward the ceiling; escalate per lane stop conditions. Silence is never success.
4. **Close out** (prefix-resumable): fence, release ticket claim, post checkpoint evidence, reap the manifest (classify; stop stragglers; mark reaped).
5. **Re-scan**: per-iteration staleness probe = newest comment/history on the epic, excluding this session's own writes and bookkeeping species — **classification routed through the species-aware `watchdog-scan.sh` output** (the partition's only skill-side consumption route; the probe is the fifth consumer, not a sixth inline copy — invoked with an **epic-only scope flag** so the per-iteration probe doesn't pay the janitor's full ≤100-children query), with the own-writes filter applied on top by run id. API authorship cannot discriminate — every plugin session writes as the same key — so "self" is session-run-id-in-body: `decision-register-entry.md` gains the run-id field alongside the other three templates (and the **RULING entry variant** — the durable resolution record for pending-human verdicts), and label/history events (which have no body to carry an id) are handled honestly — the driver skips writes it knows it just made, and any residual unattributable history event triggers a benign full re-scan, stated as accepted behavior rather than filtered by a mechanism that doesn't exist. Human app comments are distinct users and always count. Full state-reader re-scan on external change.

Per-ticket retry ceilings carry over (stagnation-counting, progress-reset).

### Park and bloat — the only two exits

Exit protocol, both: fence, post the **continuation brief** (format in-skill per the self-containment rule; repo mirror `templates/ticket-comments/continuation-brief.md` for validation — the `decision-register-entry` precedent), `driver-claim.sh release` with exit state, exit. Brief-post failure: retry once, then exit anyway — durable state alone is the proven cold-boot path.

## The Human-Ruling Resolution Route

0.13 defined only the pending-human *hold* ("escalate and leave the label; `coherence-pending` stays until the human rules") — no answer route. This section is that route, defined **once**; the guard, boot queue, and the tick's 2.2 reference it and never restate it.

**The answer surface is a session, not a parsed comment.** The escalation asks the human to resolve via **`rule-coherence <merge-sha> approve | reject | redirect:<scope>`** — a thin entry point (a `drive-epic` ruling mode reusing its claim/fence/routing; no new skill) that the human runs when ready. Because the human's own session performs the routing, there is **no natural-language parse, no comment-authorship discrimination, no wake edge, and no dedicated-automation-key prerequisite** — the ruling *is* an automation-authored register write under the existing idempotent SHA-keyed discipline.

**The ruling session's full lifecycle is pinned** (a half-specified session is the collapse's one real risk — both its edges must be nailed, not just its routing middle):
1. **Acquire.** The epic is parked on the pending-human entry, so normally no driver contends. If a driver *is* live (it legitimately may be — resuming a RESUMABLE lane during the park), the ruling session **waits until that claim is released or goes stale, then acquires** — bounded, because the driver parks after at most its one in-flight lane. It never "hands off to a pickup" (no channel could deliver the ruling's content to the live driver — the collapse deleted them all); a crashed ruling session simply re-runs and re-acquires under the same wait, idempotent under SHA-keyed skip-what-exists.
2. **Route.** Read the pending entry named by `<merge-sha>`, route per flag (below), and write the `RULING` as the last write.
3. **Clear.** **Evaluate the register-wide clear predicate and clear `coherence-pending` if satisfied, in this same session** — the deleted async wake edge had *occasioned* this evaluation as well as the routing, and nothing else now owns it; without an in-session clear the epic can strand label-set-but-resolvable (worst at end-of-epic, where only the epic PR remains and no child looks actionable, so no boot is triggered). A guard backstop covers a crash between the `RULING` write and the clear: see the guard's actionable-work test.
4. **Exit.** **Release the claim with a `ruled` exit state and exit. The ruling mode never enters the drive loop and never selects from the priority table** — it must not become the driver from the human's terminal, nor idle holding a fresh claim that blocks the guard from booting a real driver.

**Per-flag routing** (the load-bearing half — the reviewer records the routing inputs at review time, the ruling session executes them):

- **GATE1_AMENDMENT.** *approve* ⇒ execute the **held route** recorded in the pending entry (canonization, superseded-by note, affected-children label strips — recorded *held*/not-yet-performed, a pinned template field). *reject* or *redirect* ⇒ the **MATERIAL_DRIFT machinery** (corrective ticket, dependents held by relation); `redirect:<scope>` scopes the corrective (judgment fed to the corrective-drafting step, not a machine-parsed field), bare `reject` scoped by the contradiction; the corrective's blocked-by relations cover the AMENDMENT's originally-held dependents, and a scope naming a child outside that set is caught at that child's own merge seam rather than pre-sequenced.
- **GATE1_REFRESH** (cumulative drift — its constituent decisions were each already individually canonized, so the register canon *itself* is what the human rules on). *approve* ⇒ the underlying writes already routed; the `RULING` records the re-approved delta as the new Gate-1 baseline (the held route is a no-op by construction). *reject* or *redirect* ⇒ **de-canonize**: post superseding register entries, update the canon summary to remove the rejected decisions, and strip readiness labels on the **per-decision affected-children set the fable reviewer recorded in the pending entry at review time** (a mechanical durable read, not inline sonnet-driver judgment, honoring the 0.13 "divergence is judged once, at the seam, by the Frontier reviewer" doctrine) — a MATERIAL_DRIFT corrective only where the scope names rework. Composes with an in-flight lane exactly as 0.13 LEGITIMATE_DIVERGENCE realignment does (the label held through the whole park; a RESUMABLE lane resumed during the park may re-read the soon-to-be-rejected canon but is caught at its own merge seam against the by-then de-canonized register — the bounded-and-detected exposure 0.13 already accepts; merge-ineligible-while-pending guarantees that seam reviews against the de-canonized register).

**Ordering and idempotence.** The route ends by writing the `RULING` register entry — the **last write** (fail-closed, the label-before-merge principle): a mid-route crash leaves the pending entry unresolved, and the human simply re-runs `rule-coherence`, idempotent under the SHA-keyed skip-what-exists discipline. The `coherence-pending` clear is evaluated *after* the `RULING` lands, **outside** the route (by the register-wide clear predicate in the merge-close-out Key Point), so a reject-branch MATERIAL_DRIFT collapse — whose 0.13 row clears the label — cannot race the ordering. The `RULING` is a `decision-register-entry.md` variant with the **same `# Decision Register Entry` header** and the same `Merge SHA:` key the audit reads; its body records the outcome (approve/reject/redirect) and the writes performed. *unresolved* ≡ a pending-human entry with no later `RULING` for its SHA — the ruling's `<merge-sha>` argument binds it. At-most-one unresolved pending-human entry is an invariant for 0.14-produced epics (halt-after-first-pending ∧ merge-ineligible-while-`coherence-pending`); only a pre-0.14 migration epic can present two ⚠ entries, which is why the SHA argument is load-bearing.

**The guard, boot, and tick simplify accordingly:** an unresolved pending-human entry is a human-wait park — they **no-op on it** (no wake edge, no arrived-but-unrouted predicate, no comment read to classify); the janitor's digest owns the reminder until the human runs `rule-coherence`. This deletes the round-9-through-12 comment-parse machinery (pinned format, parse-attempt marker, `max(createdAt,updatedAt)`, authorship gating) that the async comment surface required; the session surface needs none of it.

### Proportionality — decided: session-delivered (capstone finding, resolved)

The capstone flagged that the route's original *comment-parse answer surface* — a pinned NL ruling format, a `parse-attempt-marker` template, `max(createdAt,updatedAt)` edit detection, parse-conservatism, and a dedicated-automation-key deployment prerequisite — was over-built to parse a natural-language ruling typed as a PM comment, for an event that fires a few times a year. The tell was the design's own rule *"a manual plugin session must not relay the ruling"* — it forbade the operator's most natural act to protect machinery built for a less natural one.

**Decision (operator): collapse to session-delivered**, as written in this section — the human runs `rule-coherence`, which routes directly and writes the `RULING`. This deleted the pinned format, the parse-attempt marker (template + species + validator entry), the edit-detection recency rule, parse-conservatism, the not-a-ruling branch, the async wake edge, and the automation-key prerequisite — roughly half the original section — for zero parse ambiguity and one fewer deployment constraint. The **load-bearing half is untouched**: the pending-human definitions, the `RULING` record and last-write ordering, the register-wide clear predicate, and the per-flag routes with the reviewer-recorded held-route / per-decision affected-children fields (a REFRESH-reject genuinely needs the recorded de-canonization sets; a blunt "reject re-opens Gate 1" would lose them). The trade accepted: the operator opens a session to rule rather than typing a chat reply — cheap for a solo-operator hive already in the loop at Gate 1 and Gate 2.

## Event-Based Await (`await-worker.sh` v2)

- **Terminal record:** finished workers end with assistant record(s) carrying `"stop_reason":"end_turn"` — verified strictly terminal across 20 live transcripts (2026-07-04, this harness version).
- **Mechanism (empirically validated):** loop checking the transcript's **final lines** every few seconds (whole-file grep is one escaping accident from false completion, and additive harness drift would be silent; last-lines keeps drift loud), mtime stall alarm in the same loop, `STALLED` distinct. ~1s match latency; correct on not-yet-existing files. (The first draft's `tail -F | grep` one-liner hangs on completion — reproduced, dead.)
- **Truncation guard (demonstrated):** large final records flush in multiple writes; after match, confirm completeness (trailing newline or one stable re-poll) before extracting.
- **Chunking:** ≤9-min chunks (harness caps verified: 600s max, 120s foreground default); chunk timeout = "still running," never "done"; self-bounding, no `timeout(1)` dependency.
- **Extraction is line-based.** In-script caveats: one-shot workers only; pattern is harness-internal serialization.

**Prompt-layer closure:** every worker prompt template (13, verified) carries the one-line await rule; `lane-dispatch-prompt.md`'s v1 mechanics restatement deleted, header renamed.

Per-session filenames: `.dodi/dispatch-manifest-<session-run-id>.jsonl`. - Mandatory at every close-out and exit; worktree removal only on clean exit after reaping, so crashed lanes leave worktree + manifest for the janitor sweep.

## Live-Test Gate (on 0.14.0, before 0.14.1 deletes `pickup-next`)

1. **Agent-tool completion notifications reach a scheduled-task session** (dual-wake primary).
2. **Background-Bash exit re-invocation reaches a scheduled-task session** (dual-wake backstop; if both disappoint, pinned fallback = foreground chunked awaits).
3. **Background-shell lifecycle**: multi-hour survival; the refresher's session-process orphan detection actually fires on session crash (mechanism pre-corrected this round — it must watch the session process, not its wrapper parent).
4. **The agent-layer stop primitive**: works; nested availability; **and the post-stop transcript shape** (does a force-stopped worker get a terminal record? — defines which STALLED confirmation branch is real).
5. **Scheduled-session longevity**: multi-hour scheduled runs permitted at all; if capped, the design degrades to a bounded-latency tick via succession — survivable, latency story restated honestly.
6. **Does a dispatched Agent-tool lane survive its dispatching session's *death*?** (Distinct from item 4, which is the stop primitive from a *live* session.) The takeover reap-before-release ordering and the reaper's "orphaned grandchildren run to completion" posture both key on this; if lanes die with the session, the takeover reap is a cheap confirm, and if they survive, it is load-bearing against a two-lanes-on-one-ticket collision.
7. **Does the scheduler fire an hourly task run while a prior run of the same task is still live?** The 0.13 corpus asserts same-task no-overlap; the whole guard-vs-live-driver cadence (wedged-probe home, in-loop heartbeat refresh) depends on the answer. No-overlap ⇒ the probe is daily and the driver must self-refresh the heartbeat (as specified); overlap ⇒ pickup-next's 0.13 serialization premise was always false and the probe may re-home to the guard.
