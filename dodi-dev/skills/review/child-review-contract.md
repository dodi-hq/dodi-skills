# Child Review Contract

## TL;DR

A child receives early Capable implementation feedback, then one fresh Frontier review of completed code, tests, documentation, and epic coherence before its PR opens. Unchanged, fully covered work reuses that approval; changed or uncertain coverage requires renewed Frontier review before the next irreversible action.

## Key Points

- Early feedback does not authorize a PR or merge.
- The combined final is Frontier with **hard** availability policy on every epic and delivery tier.
- Correctness and coherence remain separate verdicts and evidence, even in one dispatch.
- Approval names the child HEAD, target epic/base, and exact decision context; HEAD alone is insufficient.
- No proposal from an unmerged child becomes canonical before a verified merge.
- Tests, local CI, sync checks, integration serialization, drift routing, and human gates remain mandatory.
- Florist requires the companion enforcement described in `florist-companion.md`; a capability guard blocks delivery on an older kernel.

## Sequence and review scope

1. Implement at the existing ticket delivery tier. Run one Capable feedback review (`review-prompt.md`) of the substantive implementation. Fix its findings at the existing fix-worker tier; repeat feedback only when needed to resolve findings, within the existing five-round cap. This gate uses `pre-pr` attribution for compatibility; it is not the final approval.
2. Complete the Testing Contract, child docs-sync, verification and local CI. Verification fixes receive the existing focused Capable review when production code changes, then rerun affected tests and local CI. Those checks do not replace the combined final.
3. Require prior coherence publication and human rulings to be settled before reading canon for final/renewal or action freshness. `coherence-pending` blocks those operations even in a resumed deliver lane; only already-scoped work consuming no new canon may use the resume exemption. Then synchronize with the current epic base, resolve only in-scope mechanical conflicts, and rerun required checks after sync. Snapshot the approved epic intent, Gate 1 signoff, decision-register canon and entries, relevant sibling specs/work, and child spec/plan. Capture absent legacy canon explicitly and apply the coherence prompt's bootstrap rule; unknown or partial reads do not count as absence.
4. Dispatch **one** fresh Frontier reviewer using `child-pr-integration-prompt.md` in `pre-open` mode. It performs the full correctness checklist on code AND tests, plus every coherence responsibility/output from `../epic-orchestrator/coherence-reviewer-prompt.md` in proposal mode, directly in the same leaf. Both scopes must be explicit in its report. No automatic Capable+Frontier integration pair follows this gate.
5. Fix findings at the existing delivery tier, rerun affected checks and local CI, then dispatch a fresh Frontier renewal covering the fix and its interactions plus the full coherence context. Five final/renewal rounds per attempt; an exhausted cap escalates, never approves. A first final always reads the full child diff; a renewal may focus substantive correctness on the delta only when its prior full coverage is available. It still reads the full current diff for unintended changes and re-establishes both verdicts for the new identity.
6. Before opening the PR, re-read live identity and check the durable approval with the helper below. Pushes and evidence comments must not add commits. If HEAD, epic base, relevant decisions, or verification changes, return to the needed checks and Frontier renewal. Unknown freshness fails closed.
7. After opening, the child-PR seat checks PR target/head, evidence coverage/freshness and CI. At identical identity with complete clean evidence, return an explicit reuse result without a new judgment dispatch. Any changed HEAD (including tests/docs), epic base, or decision context invalidates approval; sync and verify as needed, then run one Frontier renewal. Never infer that a change is harmless from filenames alone. This conservative experiment renews even on a docs-only identity change.
8. In the serial merge slot, repeat the live coverage check immediately before merge. Keep the existing sync/CI and adoption-evidence rules. No merge is allowed on a stale or partial approval. A slot authorizes no decision-context rewrite and no substitution for Frontier. Re-read authoritative relevant decisions immediately before acting and invalidate any detected drift. The slot serializes kernel-owned integration, not external tracker edits; a residual external check/action race remains and must not be described as atomic fencing.

## Evidence and freshness

Florist may perform steps 7–8 deterministically without a provider session when its implemented kernel path validates the same complete evidence and live identity, preserves lane/pin/lease/slot checks, and records an explicit reuse receipt. This is a kernel state transition, not a fabricated worker digest or reviewer round. If a provider seat is dispatched, it must still close its normal digest. Changed or uncertain coverage requires the worker path for sync, checks or Frontier renewal. Count substantive reviewer invocations separately from any remaining provider coordinator sessions.

Persist a review JSON attachment in the existing Seat Record / Lane Checkpoint (outside the child commit, to avoid changing the reviewed HEAD). Preserve the raw reviewer report, context snapshot, runner digests and `review-executor:` record there. A local `.dodi/` copy is a cache, not the durable source. Only a completed dispatched review with qualified runtime-local Frontier evidence can issue approval; a helper pass validates the record, not the truth of an agent's claims. Native evidence follows the existing `source=dispatch` trust boundary: the dispatcher records the actual request and report, not a provider-attested execution proof. No signed attestation or new nested-dispatch protocol is implied.

`python3 "${CLAUDE_PLUGIN_ROOT}/scripts/child-review-gate.py" check <review.json> <current.json>`

In Florist, success additionally carries `artifact ref=child-review:<safe-relative-locator> sha=<head>`; the recommended local cache is `.dodi/florist-child-review.json`, never committed. The kernel must validate the path and ingest the record and linked report evidence into immutable durable storage; the local cache is not authoritative. The record uses `schema: 1`, `identity` with `repo`, `child_ref`, `child_head`, `epic_ref`, `epic_head`, `context_sha256`; `correctness: "Approved"`; `coherence: {verdict, flags: []}`; `executor: {tier: "Frontier", policy: "hard", qualified: true, model, effort, evidence}`; and `verification: {head, status: "passed", local_ci_head, evidence}`. `evidence` fields are nonempty durable locators. The dispatcher copies native model/effort from the real dispatch and checks qualification per `execution-model.md`, not from a worker's self-description.

The Florist transport extends this same schema-1 record with `reports: {review, dispatch, verification}` (each a nonempty full-text report) and `proposal: {canon, entry, affected: [unit ids]}`. Preserve every coherence output, including per-child label/readiness mappings, held routes and corrective drafts, in `reports.review`; `affected` is only a summary, not authorization to infer routing. `canon` is the full intended canonical section, including the current section for an explicit no-change result, never an accidental empty replacement. An empty affected list is valid. The kernel binds the complete immutable envelope to a content-SHA256 receipt; distinct renewal evidence must not overwrite an earlier receipt even at the same identity. Reuse retains the original reports and executor. The local helper validates the base review contract and permits these extra fields; the kernel additionally validates the transport envelope and publication obligations.

`current.json` contains that same `identity`, `clean_worktree: true`, `current_with_epic: true`, and `canon_ready: true`, collected afresh from git, remote PR/branch reads and the authoritative decision sources. `child_head` is the pushed remote HEAD, equal to local HEAD. `epic_head` is the fetched current remote target HEAD, verified as an ancestor of the child. Repo and branch identities must match the intended PR, not just the SHA. `canon_ready` means no unresolved prior coherence publication or human ruling; it does not mean the integrating worker lacks its own serial slot. In manual mode require the prior `coherence-pending` barrier clear before the final/action check; setting the orchestrator's own pre-merge fence afterward does not authorize a new review through an unresolved prior barrier. Never copy the approval's fields to construct the live input.

Produce `context_sha256` with `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/child-review-gate.py" context <snapshot.json>`. The snapshot includes `epic_id`, `approved_intent`, `gate1_signoff`, `canon`, `register_entries`, `siblings`, `spec`, and `plan`, with stable source ids/revisions and the complete relevant approved content. Sort entry/sibling lists by stable id; exclude only bookkeeping such as Seat Records and the proposal itself, not semantic register decisions or human rulings. `siblings` covers relevant delivered interactions via the epic HEAD and relevant pending sibling specs/interfaces; state the interaction scope. Do not pull unrelated sibling content. Capture the same sources again at each freshness check. Incomplete pagination, missing source access, or uncertain relevance is a blocker. This is content identity, not a timestamp-only cache.

Florist supplies `FLORIST_CHILD_REVIEW_INPUT_COMMAND` as a JSON argv array and `FLORIST_CHILD_REVIEW_INPUT_PATH` for the resulting `{identity, context}` JSON. **Run the command before reading the path**, initially and before each final/renewal or freshness check; the file may not exist at launch. Invoke without a shell, for example `python3 -c 'import json, os, subprocess; subprocess.run(json.loads(os.environ["FLORIST_CHILD_REVIEW_INPUT_COMMAND"]), check=True)'`. A failed command or missing input blocks; never reuse an old file after refresh failure. The command reads live pushed child/base, tracker decisions and committed spec/plan using the companion's shared snapshot algorithm; preserve its `context` object unchanged (that object, not the outer envelope, is the input to the hash helper). Verify the returned identity matches the actual review target; do not copy a launch identity after code changes. Kernel topology, admission, or sibling approval-readiness changes require redispatch because the command's exported metadata is dispatch-scoped. The sibling manifest's lane and accepted contract SHA determine which approved artifacts are expected: known not-yet-approved absences are explicit hashed inputs, while an unreadable expected approved source blocks. The kernel re-reads barriers and semantic source metadata after slow external reads and independently reconstructs current action-time identity; this worker snapshot is neither an external lock nor proof of `canon_ready`, which remains a kernel-owned barrier check.

Code/test/docs commits always invalidate the child SHA. Epic base movement invalidates approval even when previously allowed by a de-minimis sync exception; the child-review approval rule is stricter. Context-only movement also invalidates approval, even at the same two git SHAs. Run required CI after code/base changes; a context-only renewal may cite still-valid CI at the unchanged HEAD if the Testing Contract has not changed. Every reuse emits `review-reuse: <stage> source=<record> child=<sha> epic=<sha> context=<sha256>` plus the live helper result; preserve the original executor evidence and ledger, never fabricate a new Frontier dispatch or a zero-round ledger.

## Coherence proposals and publication

The combined reviewer must produce all existing coherence verdict fields: alignment verdict, divergence justification, register-entry proposals, affected children and label mapping, Gate 1 amendment/refresh flags and held routes, corrective draft where applicable, and proposed canon text. Record them on the child as a **proposal**, never as a merged `Merge SHA:` register entry. The coherence sub-verdict gets `caught-by: coherence/<round>/<tier>`; correctness uses `child-pr/<round>/<tier>`. One dispatch may produce both evidence scopes but must not be counted as two model calls.

- `ALIGNED`, `MINOR_DRIFT`, or `LEGITIMATE_DIVERGENCE` may pass only with correctness Approved, no unresolved findings, and no Gate 1 flags. Minor/legitimate drift keeps the existing explicit routing obligations; approval does not erase them.
- `MATERIAL_DRIFT` before merge blocks PR opening/merge and returns for contract correction with the corrective draft. It does not permit merging known drift just to file a corrective afterward.
- Any `GATE1_AMENDMENT` or `GATE1_REFRESH` before merge blocks PR opening/merge and escalates to the existing human specification/signoff path with the proposed held route. Do not manufacture a merge SHA or use the post-merge `rule-coherence` command for an unmerged child. After a ruling changes approved context, run a fresh Frontier review. Existing post-merge ruling semantics remain unchanged for legacy/audit cases.
- `ALREADY_REVIEWED` is only reusable with the complete prior verdict and identical identity; it is not an approval by itself.

After a verified child merge, publish the staged coherence proposal under the real merge SHA, serially and idempotently, then apply the existing verdict routing and canon/affected-child writes. Manual delivery retains its squash method; Florist retains its existing `merge_method=merge`. Prove the merged commit's first parent equals the reviewed epic base and its tree equals the reviewed child tree before transferring the approval. Preserve the child/base/context identity and original executor record in the merged entry. If proof is absent or false, keep `coherence-pending` and dispatch a hard Frontier audit of the actual merged result; never relabel unrelated evidence. Retain the merged-SHA set-difference audit as the crash/external-merge backstop, but transfer valid proposals without another compulsory review. No pending proposal changes canon, strips sibling labels, or counts toward that audit before the merge succeeds.
